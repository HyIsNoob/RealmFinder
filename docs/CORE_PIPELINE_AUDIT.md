# RealmFinder core pipeline audit

Date: 2026-09-23. Scope: all Java source in `src/main`, `src/client`, and `src/test`, plus mod metadata, mixin configs, Gradle configuration, and README. This is a source audit; the Minecraft client and a multiplayer server were not exercised.

## Current pipeline

| Stage | Current implementation |
| --- | --- |
| Camera and input | `CameraItem.use` invokes a client callback. `PhotoCaptureHelper` waits for `WorldRenderEvents.END`, crops the framebuffer, saves a local PNG, then sends `TakePhotoPayload` with a client supplied camera pose, FOV, depth and UUID. |
| Server capture | `ModPackets` checks for a camera. `ViewfinderEngine.capture` scans an axis-aligned box around a frustum, stores non-air/non-bedrock block centers and block entity NBT, and stores up to 16 eligible entities. |
| Snapshot and item | `WorldSnapshot` contains a block-state palette, camera-space coordinates, entity NBT and metadata. `SnapshotSerializer` writes a GZIP block stream plus NBT palette/entities into the Photograph's `CUSTOM_DATA` component. The PNG is stored separately on the capturing client. |
| Preview and alignment | `ViewfinderOverlayRenderer` draws the original PNG in a screen-space square and an angle/scale HUD. `FrustumGhostRenderer` is disabled. It does not project the snapshot into the target world or show the blocks that will be replaced/carved. |
| Placement | `PhotographItem.use` sends `StampPhotoPayload`. The server reads a held Photograph, decodes it, and `ViewfinderEngine.stamp` snaps yaw/pitch, scales camera-space coordinates, maps them to block positions, optionally carves the bounding box, places blocks in two passes, restores block entity NBT and spawns entities. The server then saves an Undo record and consumes one Photograph in survival. `PhotoStandBlock` invokes the same engine through a separate server path. |
| Undo | `UndoManager` keeps up to 10 records per player in a static in-memory map. `UndoRecord` stores previous block states, block entity NBT, spawned entity UUIDs and a Photograph copy; Z sends `UndoPayload`, and `/realmfinder undo` uses the same manager. |
| Other state | The Photo Album stores up to 18 Photograph stacks in its own item component on menu close. Photo Stand stores a Photograph in a block entity. There is no mod configuration or persistent Undo store. The two example mixins are no-ops; `MouseScrollMixin` changes client-only scale. |

## Highest-priority findings

1. **Critical: untrusted client pose and size can drive world reads/writes.** `ModPackets` uses packet eye coordinates, yaw, pitch, FOV and far plane for capture and placement without checking proximity to the server player, finite values, sane ranges, world border, loaded chunks, capture volume or placement size. A modified client can request remote captures, remote stamps or an enormous main-thread scan. The item and camera checks do not constrain where the action occurs. See `ModPackets.java:39-56,75-104`, `ViewfinderEngine.java:64-96,160-181,206-272`, and both payload records.

2. **Critical: Undo can duplicate photos and erase unrelated world state.** `UndoRecord` copies the entire held stack before the server removes just one item. Undo returns that entire stack; creative mode does not consume anything yet still returns a copy. The Photo Stand path never removes the mounted photo, but also pushes a record that returns a copy. Repeated stand clicks stamp repeatedly. Undo discards *every* item entity in a broad box, including items unrelated to the stamp, and blindly restores blocks that another player may have changed. See `ModPackets.java:101-124`, `PhotoStandBlock.java:127-149`, `UndoRecord.java:27-29,61-112`.

3. **Critical: no bounded, validated snapshot format.** `SnapshotSerializer.fromNbt` accepts a block count and per-block NBT byte length without upper bounds or schema version; malformed or oversized item data can allocate heavily, fail during decode, or drive an oversized placement. Errors in the compressed stream are printed and a partial snapshot is returned. Stored block entities include inventory contents; captured entities include arbitrary saved NBT. This permits item/entity duplication through ordinary repeated captures and can carry expensive data. See `SnapshotSerializer.java:96-171`, `ViewfinderEngine.java:108-114,121-149,347-360`.

4. **High: the placement preview does not describe the resulting world.** The held-photo HUD draws the original bitmap at the screen center, while placement snaps yaw to 90-degree steps, pitch to 45-degree steps, floors transformed coordinates, dilates blocks at 2x/3x, overwrites occupied positions, and carves other positions. It shows neither target block coordinates nor collisions, unloadable chunks, destructive changes or entity spawn locations. The client starts its success animation before server acceptance. See `ViewfinderOverlayRenderer.java:75-88,101-177`, `RealmFinderClient.java:52-69`, `ViewfinderEngine.java:177-273`.

5. **High: Undo is tied to the player's current dimension and server process.** Records contain no dimension; `UndoManager.undo` passes `player.serverLevel()` at undo time. After portal travel, it may restore the same coordinates in the wrong dimension and return the photo. The static map also survives neither restart nor a clean server lifecycle and is not scoped to a particular server instance. See `UndoManager.java:18-40`, `UndoRecord.java:22-29,47-118`.

6. **High: placement has no atomic validation or reliable failure result.** Carving and block writes start before the server knows whether all target chunks are loaded, blocks may be replaced, entities may spawn, or the item should be consumed. `stamp` returns `void`; even an empty or fully skipped snapshot is followed by Undo push, effects and Photograph consumption. `setBlock` and `addFreshEntity` return values are ignored. See `ViewfinderEngine.java:160-164,254-360`, `ModPackets.java:101-124`.

7. **High: photographed images are local files, outside the item and multiplayer sync.** Other players and a new client installation receive only the UUID, then use a placeholder because `realmfinder_photos/<UUID>.png` exists only on the capturing machine. Dynamic textures are cached without eviction, so a long session keeps image memory indefinitely. See `PhotoCaptureHelper.java:23,65-102,151-170`, `ViewfinderOverlayRenderer.java:177`.

8. **Medium: block transform and placement rules lose information.** Block state rotation uses only yaw while geometry changes with pitch. At non-cardinal capture yaw, a snapped target camera rotates positions by one angle and block states by rounded `deltaYaw`; multiblock structures, rails, doors and directional attachments can be inconsistent. At 0.5x several source blocks collapse into one map entry and iteration order decides the winner. At 2x/3x block entities and fragile blocks remain one block while surrounding geometry grows. See `ViewfinderEngine.java:177-248,284-303`.

9. **Medium: the captured image and voxel selection have different inputs.** The PNG is taken from the rendered frame, but the server's selection uses a later packet pose and server world state. Auto-focus depth is picked at the crosshair after screenshot capture and can omit distant visible terrain. `containsBlock` includes blocks by corner overlap, which can select voxels not visibly represented by their center. Motion, latency, FOV effects and dimension transitions can widen the mismatch. See `PhotoCaptureHelper.java:126-191`, `ViewfinderEngine.java:93-115`, `Frustum.java:70-95`.

10. **Medium: Album lifetime and Photograph hand selection need explicit ownership.** The Album's temporary container writes back to the original `ItemStack` only on menu close, and `stillValid` checks the temporary container rather than whether the player still owns that same Album. The stamp packet identifies neither hand nor Photograph ID, so a changed main hand or offhand between click and server execution may consume/place a different Photograph. See `PhotoAlbumItem.java:29-40`, `PhotoAlbumMenu.java:58-68`, `ModPackets.java:75-91`.

## Recommended order

1. **Contain world changes:** validate packet pose and capture limits server-side, check dimensions/loaded chunks/world border, cap total block and entity operations, and reject malformed snapshots before any mutation. Return a specific failure reason to the client.
2. **Make stamp/Undo transactional:** build a placement plan, validate it, apply it, then consume exactly one identified Photograph. Record the source dimension and exact changes. Undo should check conflicts and only remove entities/drops created by that placement. Put Photo Stand through the same transaction and consume or otherwise explicitly define its ownership rule.
3. **Make preview truthful:** derive preview and validation from the same placement plan/transform, and show prospective writes, carving, conflicts and invalid destinations before click. Keep the PNG as photographic presentation; use projected world geometry for placement certainty.
4. **Bound and version snapshots:** add schema/version checks, limits for compressed/decompressed data, palette indices, coordinates, entity types and NBT. Define policy for inventory-bearing blocks/entities and entity duplication. Ensure corrupt data fails closed.
5. **Handle multiplayer image delivery and persistence:** give all viewers a bounded image representation or render a deterministic thumbnail from snapshot data; release textures when unused. Choose durable Undo semantics and communicate them in game.
6. **Polish after correctness:** tune FOV/depth capture, scale rules, directional blocks, feedback and controls with real client/server scenarios.

## Verification baseline and gaps

`gradlew.bat test build --console=plain` completed successfully on 2026-09-23. The tests in `MathAndFrustumTest` cover camera basis, frustum point checks and examples of transform/scaling arithmetic. They do not invoke the packet receivers, actual world capture/stamp, serialization of malformed data, inventory flows, Undo, Photo Stand, or multiplayer behavior. Before claiming gameplay safety, exercise those paths on a disposable world and a dedicated server with at least two players, including dimension travel, unloaded chunks, filled inventories, inventory-bearing blocks and disconnect/reconnect.
